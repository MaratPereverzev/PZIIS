# Лабораторная работа №2 по ПЗИИС

Часть 2.1 — «Оценка защищённости разработанного приложения».

## Что здесь

`pziis-vault` — веб-приложение с разделением данных на **конфиденциальные**
и **неконфиденциальные**, разработанное под требования задания 2.1, и его
анализ защищённости по четырём позициям, заданным методичкой.

| Требование задания | Реализация |
|---|---|
| Добавить пользователя в систему | `POST /register`, `POST /admin/accounts` |
| Авторизовать по идентификационным данным | `POST /login` (Argon2id + серверная сессия) |
| CRUD и поиск **конфиденциальных** данных | `/secrets/*` — AES-256-GCM, поиск по слепому индексу |
| CRUD и поиск **неконфиденциальных** данных | `/notes/*` — открытое хранение, поиск по `tsvector` |
| Деавторизовать пользователя | `POST /logout`, `POST /logout/all` |

Приложение работает на базе `app_db`, схеме `app` и ролевой модели
(`admin_role` / `user_role` / `guest_role`), настроенных в лабораторной
работе №1: та же политика безопасности СУБД переиспользуется, а не
создаётся заново.

## Запуск

Требуется Docker с плагином Compose. Всё выполняется в контейнерах —
на рабочей машине ничего не устанавливается и не изменяется.

```bash
./run.sh      # генерирует .env и сертификат, собирает и поднимает стенд
./check.sh    # 56 автоматических проверок защищённости
./demo.sh     # 12 сценариев демонстрации защищённости
docker compose down -v   # остановить и удалить всё
```

После `./run.sh` приложение доступно на <https://127.0.0.1:8443/>.
Логин и пароль администратора скрипт печатает при первом запуске
(и хранит в `.env`, права `600`, в репозиторий не попадает).

Сертификат самоподписанный — браузер предупредит. Это осознанное
ограничение стенда, зафиксированное в анализе: без сертификата доверенного
удостоверяющего центра защита от атаки «человек посередине» неполна.

## Ключевые проектные решения

- **Разделение классов данных доведено до уровня хранения**: разные
  таблицы, разные привилегии, разные механизмы поиска, разные политики
  построчной защиты. Смешать их нельзя структурно.
- **Двухконтурный контроль доступа**: право проверяется в коде (роль и
  владелец) и независимо в СУБД (политики RLS по локальному параметру
  транзакции `app.actor_id`). Ошибка в одном контуре не открывает данные.
- **Поиск по зашифрованным данным** через слепой индекс
  `HMAC-SHA256(K_idx, owner_id ‖ token)`. Это центральный компромисс
  работы: требование «поиск конфиденциальных данных» несовместимо со
  стойким шифрованием, и цена решения названа прямо — утечка равенства и
  частоты токенов в пределах одной учётной записи.
- **Администратор не читает открытый текст чужих записей**: обзор идёт
  через представление метаданных. Осознанное отступление от формулировки
  методички 1.2 «полный доступ ко всем подсистемам», обоснованное
  разделением обязанностей и CWE-250.
- **Деавторизация мгновенная**: сессия — opaque-токен, в базе только его
  SHA-256, выход удаляет строку. JWT здесь не подошёл бы: отозвать его
  до истечения срока подписи невозможно.

Подробности и обоснования — в `docs/01-design.md` и `docs/02-analysis.md`.
