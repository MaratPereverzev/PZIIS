# Лабораторная работа №2, часть 1. Анализ защищённости приложения

Анализ выполнен по четырём позициям, заданным методичкой 2.1, п. 2.
Для каждой меры указано, **что именно** она закрывает и **какой риск
остаётся** — необоснованное «всё защищено» на защите не принимается.

---

## 1. Политика безопасности операционной системы

### Что сделано

| Мера | Закрываемая угроза |
|---|---|
| Сервис работает от непривилегированного `pziis`, а не от `root` | эксплуатация уязвимости в приложении не даёт прав администратора ОС (CWE-250) |
| Код `0750 root:pziis` — приложение не владеет своим кодом | невозможна модификация исполняемого кода из скомпрометированного процесса |
| `keys.env` `0640 root:pziis` | ключи недоступны прочим пользователям системы; читаются процессом, но не перезаписываются |
| `NoNewPrivileges=yes`, `CapabilityBoundingSet=` пуст | обрыв цепочки повышения привилегий через setuid/capabilities |
| `ProtectSystem=strict` + `ReadWritePaths` | запись возможна только в каталог журналов; закладку в систему не положить |
| `PrivateTmp=yes` | нет атак через предсказуемые имена в общем `/tmp` (CWE-377) |
| `MemoryDenyWriteExecute=yes`, `SystemCallFilter=@system-service` | затруднено исполнение внедрённого кода и вызов «экзотических» сисколов |
| `umask 0027`, отсутствие setuid-бинарей | создаваемые файлы недоступны посторонним по умолчанию |
| Каталог данных PostgreSQL остаётся `0700 postgres:postgres` (из лабы №1) | файлы БД недоступны даже пользователю `pziis` — чтение только через СУБД по SCRAM |

Прямая преемственность с лабой №1: аппарат прав ФС из части 1.1 применён к
каталогам приложения, а разграничение доступа к СУБД из части 1.2 —
к соединению приложения с базой.

### Остаточные риски

- Пользователь `pziis` может читать `keys.env`. Иначе приложение не
  расшифрует данные — это принципиальное ограничение схемы с ключом на том
  же хосте. Радикальное решение (HSM, внешний KMS) выходит за рамки работы;
  в отчёте фиксируется как направление развития.
- Сохранение состояния процесса в swap может вынести ключ на диск.
  Смягчение: `swapoff` в демонстрационной ВМ либо шифрование раздела
  подкачки.
- `root` компрометирует всё. Защита от вредоносного администратора ОС
  средствами приложения невозможна и не заявляется.

## 2. Политика безопасности компонентов и их взаимодействия

### Что сделано

**Приложение → СУБД.** Соединение идёт под ролью `vault_app`, у которой
нет `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `BYPASSRLS` и никаких прав DDL.
Из привилегий выданы только `SELECT/INSERT/UPDATE/DELETE` на шесть таблиц
схемы `app`, и на журнал аудита — **лишь `INSERT` и `SELECT`**. Следствие:
скомпрометированное приложение не может ни изменить структуру базы, ни
создать роль, ни затереть следы своих действий в журнале.

**Двухконтурный контроль доступа.** Права проверяются дважды и независимо:
в коде (RBAC-декоратор + проверка владельца) и в СУБД (RLS-политики по
`app.actor_id`). Ошибка в одном контуре не открывает данные — это и есть
эшелонированная защита в её проверяемом виде. Ключевой инвариант:
`SET LOCAL app.actor_id` действует только до конца транзакции, поэтому
значение не переносится между запросами через пул соединений.

**Защита от инъекций.** Все запросы — параметризованные через psycopg 3;
конкатенации строк в SQL нет. Даже при гипотетическом промахе RLS
ограничивает выборку строками текущего владельца, а `vault_app` не может
выполнить DDL. Валидация входа — Pydantic-моделями (белый список полей).

**nginx → приложение.** Взаимодействие по loopback; uvicorn не слушает
внешний интерфейс, поэтому обойти прокси и его лимиты нельзя.

**Секреты.** Пароль к БД и мастер-ключ — только в `keys.env`. В коде,
в git и в образе контейнера их нет (CWE-798).

**Обработка ошибок.** Наружу — обобщённые сообщения; текст исключения
СУБД и трассировка идут в журнал сервера (CWE-209). Версии компонентов не
раскрываются: `server_tokens off`, `/healthz` отвечает только статусом.

**Обзор для администратора без раскрытия данных.** Метаданные
конфиденциальных записей читаются из представления `app.secret_metadata`,
принадлежащего `postgres`: оно обходит RLS таблицы (это нужно для обзора),
но не отдаёт ни одного столбца с шифротекстом.

**Целостность журнала.** `audit_event` доступен приложению только на
добавление; открытые данные в него не пишутся — исключительно
идентификаторы объектов, поэтому журнал не становится вторым, незащищённым
хранилищем конфиденциальной информации.

### Остаточные риски

- RLS опирается на корректную установку `app.actor_id`. Забытый вызов
  превращает политику в «ничего не видно» (безопасный отказ), но
  подстановка **чужого** id в коде обойдёт оба контура. Компенсация: id
  берётся только из проверенной сессии и нигде не принимается из запроса;
  на это нужен отдельный тест.
- Уязвимость в самой зависимости (FastAPI, psycopg, `cryptography`)
  анализом не покрывается. Компенсация: фиксация версий в
  `requirements.txt` с хешами и регулярный `pip-audit`.
- Слепой индекс считается в приложении, значит `K_idx` живёт в его памяти;
  дамп памяти процесса раскрывает ключ индексации.
- Ограничение «администратор не читает открытый текст» держится на коде,
  политике RLS и представлении метаданных, **но не на криптографии**:
  ключ `K_enc` принадлежит сервису, поэтому сервис технически способен
  расшифровать любую запись. Ошибка в проверке роли или новый обработчик,
  вызывающий расшифровку вне контекста владельца, снимут ограничение.
  Криптографическая гарантия требует ключа на пользователя (см. раздел 8).

## 3. Сетевая политика безопасности

### Что сделано

| Мера | Закрываемая угроза |
|---|---|
| TLS 1.2/1.3, только AEAD-шифронаборы, HSTS | анализ трафика сниффером, «человек посередине», понижение до HTTP |
| Cookie с флагом `Secure` | утечка токена сессии по незащищённому каналу |
| uvicorn на `127.0.0.1` | сервер приложений недостижим извне, лимиты прокси не обойти |
| PostgreSQL `listen_addresses='localhost'` + SCRAM-SHA-256 | нет сетевого доступа к СУБД; пароль не передаётся в открытом виде |
| `ufw default deny incoming`, открыт только 443 | сокращение поверхности атаки до одного порта |
| Rate limit 10 r/s общий и 5 r/min на `/login` | перебор пароля и словарная атака по сети, примитивный flood |
| `client_max_body_size 64k`, таймауты чтения | исчерпание ресурсов большими запросами и Slowloris |
| `SameSite=Strict` + CSRF-токен | межсайтовая подделка запроса |
| CSP `default-src 'self'`, автоэкранирование Jinja2 | XSS и, как следствие, кража данных из браузера жертвы |
| `X-Frame-Options: DENY`, `frame-ancestors 'none'` | clickjacking |

### Остаточные риски

- Самоподписанный сертификат в демонстрационной ВМ: защита от MITM
  формально неполна, пока сертификат не выпущен доверенным УЦ. Заявляется
  прямо, не замалчивается.
- Полноценная распределённая DoS-атака мерами уровня одного хоста не
  отражается — нужен вышестоящий фильтр или CDN. Реализованные лимиты
  рассчитаны на одиночный источник.
- Argon2 с памятью 64 МиБ сам является ресурсом: массовый поток запросов
  на `/login` способен исчерпать RAM. Именно поэтому лимит на `/login`
  стоит **до** приложения, на nginx, а не внутри него.

## 4. Защищённость конфиденциальных данных

### Что сделано

**Разделение классов данных доведено до уровня хранения.** Конфиденциальные
записи лежат в отдельной таблице, зашифрованными, с отдельным механизмом
поиска и отдельной RLS-политикой. Неконфиденциальные — в открытом виде с
полнотекстовым индексом. Смешать их невозможно структурно, а не «по
договорённости».

**Пароли.** Argon2id (64 МиБ, t=3, p=4), соль на каждый пароль,
автоматический перехеш при усилении параметров. Восстановление пароля из
дампа таблицы `account` экономически нецелесообразно; радужные таблицы
неприменимы из-за соли.

**Тело конфиденциальных записей.** AES-256-GCM, уникальный nonce на каждое
шифрование, AAD привязывает шифротекст к `ext_id`, владельцу, версии ключа
и имени поля. Дамп таблицы `secret_record` без ключа из файловой системы
не даёт ни открытого текста, ни возможности незаметно подменить запись
(GCM обнаружит любую модификацию).

**Токены сессий.** В базе только `SHA-256` от токена — дамп `session` не
позволяет переиграть чужую сессию. Отзыв мгновенный: деавторизация удаляет
строку.

**Разделение ключей.** `K_enc` и `K_idx` выведены из мастер-ключа через
HKDF с разными `info` — компрометация индексации не влечёт компрометации
шифрования.

**Ограничение полномочий администратора.** Расшифровка возможна только в
контексте владельца записи. Компрометация административной учётной записи
даёт метаданные и управление системой, но не открытый текст чужих
секретов.

**Гигиена утечек.** Конфиденциальные данные не попадают ни в журнал
аудита, ни в журналы сервера, ни в сообщения об ошибках, ни в URL (поиск
секретов идёт `POST`-запросом, чтобы поисковая фраза не осела в
access-логе nginx и в истории браузера — распространённый недосмотр).
Ответы с секретами помечены `Cache-Control: no-store`.

### Остаточные риски

- **Главный, и он проектный:** слепой индекс раскрывает равенство и
  частоту токенов заголовков. Для словарных значений возможен частотный
  анализ. Ограничено четырьмя мерами: идентификатор владельца входит в
  вычисление тега (поэтому анализ не выходит за пределы одной учётной
  записи), индексируется только заголовок, тег усечён до 16 байт, токены
  короче 3 символов не индексируются. Это осознанная цена за исполнение
  требования «поиск конфиденциальных данных» — то самое место, где
  безопасность обменена на функциональность, и именно так это надо
  подавать на защите.
- Ключ и шифротекст находятся на одном хосте: компрометация хоста
  раскрывает данные. Шифрование защищает от кражи дампа, резервной копии
  или диска, но не от полного захвата машины.
- Открытый текст неизбежно присутствует в памяти процесса во время
  обработки запроса; Python не позволяет надёжно затирать `str`.
- Метаданные не скрыты: количество записей, их размеры и время
  изменения видны при доступе к базе.
- Резервные копии наследуют защищённость шифрования данных, но
  ответственность за сохранность ключа переходит на процедуру бэкапа —
  организационная мера, выходящая за границы приложения.

## 5. Матрица «атака → мера → остаточный риск»

Перечень атак взят из теоретических основ методички 2.1.

| Атака | Реализованное противодействие | Остаточный риск |
|---|---|---|
| Полный перебор пароля | Три рубежа: лимит 5 r/min на адрес в nginx, тот же лимит в приложении, блокировка учётной записи на 15 мин после 10 неудач; Argon2id 64 МиБ; единый текст ошибки | лимит на адрес связывает раньше порога блокировки, поэтому с одного источника блокировка недостижима — она адресована именно распределённому перебору, который замедляется, но не исключается |
| Перебор по словарю | минимум 12 символов, проверка по списку скомпрометированных паролей | пользователь всё равно способен выбрать слабый, но формально валидный пароль |
| Анализ трафика (сниффер) | TLS 1.2/1.3, HSTS, `Secure`-cookie, СУБД только на loopback | самоподписанный сертификат в демо-ВМ |
| Человек посередине | TLS + HSTS; в эксплуатации — сертификат доверенного УЦ | без доверенного УЦ защита неполна |
| SQL-инъекция | параметризованные запросы; RLS как второй контур; роль без DDL | уязвимость в самом драйвере |
| XSS | автоэкранирование Jinja2, CSP `default-src 'self'`, `HttpOnly` на cookie | ошибка при явном выводе «сырого» HTML |
| CSRF | `SameSite=Strict` + CSRF-токен для небезопасных методов | — |
| Фиксация / кража сессии | пересоздание id при входе, opaque-токен 256 бит, хеш в БД, двойной таймаут, серверный отзыв | кража токена при полной компрометации браузера жертвы |
| Повышение привилегий | RBAC + проверка владельца + RLS; администратор без доступа к открытому тексту | ошибка в проверке владельца обходит оба контура |
| DoS / DDoS | лимиты nginx, ограничение тела, таймауты, Argon2 за лимитом | распределённая атака требует вышестоящего фильтра |
| Инъекция ОС-команд | приложение не вызывает внешние процессы вовсе | — |
| Раскрытие через сообщения об ошибках | обобщённые ответы, детали только в журнал сервера | — |
| Перечисление учётных записей | единый текст ошибки, Argon2 по фиктивному хешу для выравнивания времени ответа | тайминг-канал через различие лимитов |
| Кража дампа БД / диска | AES-256-GCM, Argon2 для паролей, хеши токенов, ключ вне БД | частотный анализ слепого индекса |
| Подмена записи в БД | AEAD с AAD, привязанным к `ext_id`, владельцу и полю | — |
| Затирание следов | журнал аудита без `UPDATE`/`DELETE` для роли приложения | `root` или `postgres` по-прежнему могут |
| Социальная инженерия | техническими средствами не закрывается | требует организационных мер и инструктажа |

Соответствие CWE, на которые опирается анализ: CWE-89 (SQL-инъекция),
CWE-79 (XSS), CWE-352 (CSRF), CWE-384 (фиксация сессии), CWE-522
(недостаточно защищённые учётные данные), CWE-256/CWE-257 (хранение
паролей), CWE-311/CWE-312 (отсутствие шифрования данных при хранении),
CWE-319 (передача в открытом виде), CWE-250 (излишние привилегии),
CWE-209 (утечка информации через сообщения об ошибке), CWE-798
(зашитые учётные данные), CWE-307 (отсутствие ограничения попыток
аутентификации), CWE-204 (различие ответов, раскрывающее существование
учётной записи), CWE-377 (небезопасный временный файл).

## 6. План демонстрации защищённости

Методичка требует не только демонстрации работы, но и демонстрации и
**обоснования** защищённости. Ниже — сценарии, каждый из которых
показывается на сдаче.

1. **Хранение паролей.** `SELECT login, pwd_hash FROM app.account` —
   в выдаче строки Argon2id PHC, ни одного открытого пароля.
2. **Шифрование конфиденциальных данных.** `SELECT * FROM
   app.secret_record` от имени `postgres` — только шифротекст. Рядом —
   тот же список в интерфейсе владельца в открытом виде.
3. **Работа RLS.** Войти пользователем A, создать секрет; из сессии
   пользователя B попытаться открыть его по идентификатору — отказ.
   Затем то же самое напрямую в `psql` под `vault_app` с чужим
   `app.actor_id` — ноль строк.
4. **Администратор не читает секреты.** Вход администратором: список
   записей пользователя виден по метаданным, открытый текст недоступен.
5. **Поиск по шифротексту.** Найти запись по слову из заголовка, затем
   показать в `app.secret_tag`, что в базе лежат только HMAC-теги.
6. **SQL-инъекция.** Ввести `' OR 1=1 --` в поле поиска — строка
   ищется как обычный текст. Показать журнал PostgreSQL с
   параметризованным запросом.
7. **XSS.** Сохранить `<script>alert(1)</script>` в неконфиденциальной
   записи — выводится как текст; в заголовках ответа виден CSP.
8. **Деавторизация.** Скопировать cookie сессии, выйти, подставить
   cookie обратно — доступа нет (строка сессии удалена на сервере).
   Контрпример с JWT: он остался бы валидным до истечения срока.
9. **Перебор.** 11 неудачных входов подряд — блокировка учётной записи и
   ответ 429 от nginx. В журнале аудита — 11 событий с `outcome='denied'`.
10. **Ограничение привилегий ОС.** `ps -o user,cmd -C uvicorn` — процесс
    от `pziis`; попытка записи в `/opt/pziis-vault` от `pziis` — отказ;
    `systemd-analyze security pziis-vault` — итоговая оценка exposure.
11. **Сетевая политика.** `ss -tlnp` — 8000 только на loopback, 5432
    только на loopback; `curl http://<ip>:8000` извне — соединение не
    устанавливается.
12. **Целостность журнала.** `DELETE FROM app.audit_event` под
    `vault_app` — отказ по недостатку привилегий.

| `./demo.sh` | 12 сценариев демонстрации из раздела 6 в исполняемом виде, с выводом реальных строк из базы |

Проверки запускаются в том же образе и от того же непривилегированного
пользователя, что и приложение: иначе проверка привилегий не имела бы
смысла. Текущее состояние — 56 из 56 пройдено.

### Что проверка нашла

**Дефект в сравнении CSRF-токенов.** Первый прогон
`test_write_without_csrf_token_is_rejected` упал с `TypeError: comparing
strings with non-ASCII characters is not supported`:
`hmac.compare_digest` отказывается сравнивать строки с символами вне ASCII.
Присланный атакующим токен с кириллицей приводил к ответу 500 вместо
чистого отказа 403 — то есть к необработанному исключению на пути проверки
защиты. Исправлено сравнением на байтах (`app/auth.py:157`).

Это ровно тот случай, ради которого проверки и пишутся: механизм был
спроектирован верно, а его реализация давала сбой на входных данных,
которые атакующий контролирует полностью.

**Взаимодействие рубежей защиты от перебора.** Демонстрация показала, что
лимит 5 попыток в минуту на адрес срабатывает раньше, чем порог блокировки
в 10 неудач, поэтому с одного источника блокировка учётной записи
недостижима. Это не дефект, а свойство слоёной защиты, но его нужно
называть точно: лимит на адрес закрывает перебор с одного источника,
блокировка учётной записи — распределённый перебор по одной учётной
записи, когда лимит на адрес не связывает. В `demo.sh` три рубежа
разведены и демонстрируются отдельно (сценарии 9а, 9б, 9в).

## 8. Комплекс мер по усовершенствованию

Меры упорядочены по отношению «снятый риск / трудоёмкость». Первые две
снимают остаточные риски, названные главными в разделах 4 и 2.

| Мера | Какой остаточный риск снимает |
|---|---|
| **Ключ шифрования на пользователя.** Случайный ключ данных (DEK) на учётную запись, обёрнутый ключом, выведенным из пароля пользователя через Argon2id; DEK раскрывается только на время сессии | Делает ограничение «администратор не читает открытый текст» **криптографическим**, а не логическим: сервис перестаёт быть способен расшифровать чужую запись. Цена: смена пароля требует перешифровки обёртки, потеря пароля означает потерю данных, а DEK живёт в памяти процесса на время сессии |
| **Сертификат доверенного удостоверяющего центра** вместо самоподписанного | Закрывает единственный оставшийся разрыв в защите от «человека посередине» |
| **Внешнее хранилище ключей** (HSM или KMS) вместо файла на том же хосте | Компрометация хоста перестаёт автоматически раскрывать данные; сейчас ключ и шифротекст лежат рядом |
| **Общий счётчик лимитов** (Redis) вместо памяти процесса | Лимит начинает работать при нескольких рабочих процессах и переживает перезапуск |
| **`pip-audit` в регулярном прогоне** и фиксация зависимостей по хешам | Уязвимость в зависимости обнаруживается, а не остаётся вне анализа |
| **Шифрование раздела подкачки** либо `swapoff` на стенде | Ключ и открытый текст не попадают на диск через swap |
| **Двухфакторная аутентификация** (TOTP) для роли администратора | Компрометация пароля администратора перестаёт быть достаточной |
| **Вынос журнала аудита на отдельный носитель** (append-only, другой хост) | Сейчас `root` и `postgres` всё ещё способны стереть следы |
| **Ротация ключа** с использованием заложенной колонки `key_version` | Долгоживущий ключ перестаёт быть единой точкой отказа |

Первые две меры вместе снимают оба риска, которые в разделах 4 и 3 названы
как ограничивающие: криптографическую беззащитность перед собственным
сервисом и неполноту защиты канала.

## 9. Рекомендации по безопасному использованию

1. Мастер-ключ и пароль СУБД хранить только в `/etc/pziis-vault/keys.env`
   с правами `0640 root:pziis`; не передавать через аргументы командной
   строки — они видны в `ps` любому пользователю системы.
2. Резервные копии базы шифровать отдельно: дамп содержит шифротекст, но
   без ключа он бесполезен, а вместе с утёкшим ключом — полностью читаем.
   Ключ и резервную копию хранить раздельно.
3. Не давать роль `admin` для повседневной работы: администрирование и
   работа с данными разделены намеренно.
4. Учётные записи уволенных сотрудников блокировать, а не удалять:
   блокировка закрывает сессии и сохраняет журнал аудита, удаление
   обнуляет `actor_id` в старых записях журнала.
5. Журнал аудита просматривать регулярно, обращая внимание на серии
   событий `login/denied` — это признак перебора.
6. Стенд разворачивать в одноразовой виртуальной машине или контейнере:
   демонстрационный сертификат самоподписанный, а пароли в `.env`
   генерируются для одного прогона.
7. При переносе в эксплуатацию — сначала выполнить первые две меры
   раздела 8.

## 10. Вывод

**Семантическая составляющая.** Работа показывает, что защищённость
приложения не является свойством одного механизма: она складывается из
согласованных решений на четырёх независимых уровнях — прав в
операционной системе, привилегий и политик в СУБД, конфигурации сетевого
периметра и криптографической обработки самих данных. Ключевой принцип,
проходящий через все уровни, — минимизация привилегий: процесс не
владеет своим кодом, роль СУБД не умеет DDL, приложение не может стереть
журнал аудита, администратор не читает открытый текст чужих секретов.
Второй принцип — эшелонирование: контроль доступа реализован дважды и
независимо (код и RLS), поэтому одиночная ошибка не приводит к раскрытию
данных. Третий вывод — количественный: безопасность обменивается на
функциональность, и обмен нужно называть вслух. Требование поиска по
конфиденциальным данным несовместимо со стойким шифрованием в чистом
виде; выбранный слепой индекс — измеримый компромисс с известной ценой
(утечка равенства и частоты токенов), а не «бесплатное» решение.

**Прагматическая составляющая.** Получен воспроизводимый и проверяемый
результат: схема данных с разделением классов информации, ролевая модель,
согласованная с настройкой из лабораторной работы №1, набор конкретных
конфигураций (systemd, nginx, `pg_hba.conf`, ufw) и матрица «атака → мера
→ остаточный риск», привязанная к CWE. Каждое утверждение о защищённости
сопровождается способом его проверки, что превращает раздел анализа из
декларации в исполняемый чек-лист: 56 автоматических проверок и 12
сценариев демонстрации. Практическая ценность такого подхода подтвердилась
сразу — первый же прогон вскрыл дефект в сравнении CSRF-токенов, при
котором корректно спроектированный механизм отвечал ошибкой 500 на
контролируемые атакующим данные. Спроектированные механизмы применимы за пределами
учебной задачи: аутентификация с Argon2id и серверными сессиями,
шифрование полей с AAD и версионированием ключа, слепой индекс для поиска
по шифротексту, append-only журнал аудита — типовые решения промышленных
систем. Одновременно зафиксированы границы применимости: защита не
распространяется на компрометацию `root`, на распределённый отказ в
обслуживании и на социальную инженерию — эти риски требуют
организационных и инфраструктурных мер, лежащих вне приложения.
